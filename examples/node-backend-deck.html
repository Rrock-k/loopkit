Node backend

Node.js на пальцах

Node.js — это JavaScript runtime для сервера. Он силён в I/O: HTTP, DB, files, network.

many requests
 -> one JS main thread orchestrates I/O
 -> callbacks/promises resume when data is ready
Node backend

Главное: не блокировать event loop

Event loop обслуживает клиентов. Если твой JS callback слишком долго работает, остальные запросы ждут.

// плохо для request handler
while (Date.now() < start + 5000) {} // blocks everyone

Фраза: Node scales well for I/O, but CPU-bound work must not block the main event loop.

Node backend

Event loop ≠ magic parallelism

Node не делает твой JavaScript параллельным автоматически. Он координирует async операции, а CPU-heavy JS всё равно занимает main thread.

  • network I/O часто неблокирующий;
  • fs/crypto/dns могут использовать worker pool;
  • тяжелый JSON parsing тоже может блокировать.
Node backend

Call stack, microtasks, macrotasks

sync code -> microtasks (Promise) -> event loop phases -> timers/I/O/check...

Для интервью достаточно: promises/microtasks выполняются раньше многих обычных callbacks, и бесконечная цепочка microtasks может голодать event loop.

Node backend

Async/await — это синтаксис над Promise

async function getUser(id) {
  const user = await db.user.findUnique({ where: { id } });
  return user;
}

await не блокирует весь Node process, но продолжение этой функции выполнится позже.

Node backend

Promise.all: быстрее, но осторожно

const [user, orders, settings] = await Promise.all([
  getUser(id),
  getOrders(id),
  getSettings(id),
]);
Риск

Если массив огромный, ты создаешь слишком много параллельных операций. Нужны limit/concurrency control, batch или queue.

Node backend

CPU-bound work

Если нужно реально считать: image processing, crypto, ML, large JSON, PDF parsing — подумай о worker_threads, отдельном сервисе или job queue.

API request -> enqueue job -> worker process -> result

Streams

Stream позволяет обрабатывать данные кусками, а не держать весь файл в памяти.

readableStream.pipe(transform).pipe(writableStream)

Для больших файлов, uploads/downloads, CSV exports streams часто лучше, чем Buffer целиком.

Backpressure

Backpressure — когда получатель медленнее отправителя. Если игнорировать, память растёт.

fast readable -> slow writable
without backpressure: buffer grows
with backpressure: readable slows down

Error handling в Express 5

В Express 5 rejected promises из async handlers автоматически уходят в error middleware.

app.get('/users/:id', async (req, res) => {
  const user = await getUser(req.params.id);
  res.json(user);
});

app.use((err, req, res, next) => {
  res.status(err.status ?? 500).json({ error: err.message });
});

Transactions

Transaction нужна, когда несколько операций должны стать видимыми вместе или откатиться вместе.

await db.transaction(async tx => {
  await tx.orders.create(order);
  await tx.payments.create(payment);
});

Фраза: I use transactions around multi-step state changes that must remain consistent.

Node backend

Connection pool

Backend не должен открывать новое DB connection на каждый запрос без контроля.

requests -> pool of connections -> DB
  • pool limit защищает DB;
  • слишком маленький pool = очередь;
  • слишком большой = DB overload.

Rate limit защищает backend и LLM/API бюджет.

Graceful shutdown

При deploy/restart надо перестать принимать новые запросы, дождаться текущих, закрыть DB/queue connections.

Node backend

Вопрос: объясни event loop

Node.js использует один основной JS thread, где event loop координирует callbacks/promises и I/O. Это хорошо для I/O-heavy backend, потому что запросы не блокируют поток во время ожидания сети/БД. Но CPU-heavy sync код блокирует event loop, поэтому его выносят в worker threads, отдельные процессы или background jobs.

Node backend

Вопрос: как обрабатывать ошибки в API?

Я разделяю expected errors и unexpected errors. Validation/auth/not found возвращаются с корректными status codes. Unexpected errors логируются со stack и requestId, клиенту возвращается безопасное сообщение. В Express/Nest делаю централизованный error middleware/filter, чтобы не дублировать try/catch в каждом route.

Node backend

Вопрос: как проектировать Node API?

Делаю тонкие controllers/routes, validation на входе, business logic в services/use cases, DB доступ через repositories/ORM, централизованные errors/logging. Для долгих задач — queue/jobs. Для production — auth, rate limits, tests, metrics, graceful shutdown and config validation.

Node backend

Вопрос: REST vs GraphQL

REST проще, хорошо подходит для resource-based CRUD и стандартного caching. GraphQL полезен, когда клиентам нужно гибко выбирать shape данных и агрегировать несколько ресурсов, но требует контроля complexity, authorization per field, caching strategy and N+1 mitigation.

Типовые ошибки кандидатов

  • говорить “Node однопоточный, поэтому не масштабируется”;
  • не понимать разницу I/O-bound и CPU-bound;
  • склеивать SQL строками;
  • держать большие файлы в памяти;
  • не иметь централизованной обработки ошибок;
  • не думать о authz, rate limits, logs.
